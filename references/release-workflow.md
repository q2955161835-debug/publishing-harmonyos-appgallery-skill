# HarmonyOS AppGallery 完整发布流程

本流程以当前页面和本地证据为准。AppGallery Connect 的字段、配额和按钮名称可能变化；若标签不同，先读取页面含义，不凭旧截图猜测。

## 0. 建立发布身份表

开始前记录并交叉核对：

| 字段 | 本地来源 | 平台来源 |
| --- | --- | --- |
| 开发者账号/主体 | 用户确认 | 当前登录账号 |
| 应用名称、应用 ID | 产品与发布记录 | AppGallery 应用页 |
| Bundle Name | `AppScope/app.json5` | 应用与软件包详情 |
| versionName/versionCode/buildVersion | 应用配置与 `pack.info` | 软件包解析行 |
| 设备类型、API | 模块配置与 `pack.info` | 软件包解析行 |
| 发布地区、价格、发布时间 | 发布计划 | 版本配置 |
| 源码身份 | Git commit、分支、工作区 | 发布记录 |

任一关键字段冲突就停止。不要用旧对话里的值覆盖当前文件或页面。

## 1. 发布前工程门禁

1. 读取仓库 `AGENTS.md`、README、产品边界、发布文档和验收规则。
2. 检查 `git status --short --branch`、当前提交、远程、版本文件和待发布差异。保留可回退检查点；不要混入无关脏改动。
3. 运行项目规定的静态检查、本地测试、集成/设备测试和人工清单。权限、数据、部署或核心流程按项目要求完成 L3 验收。
4. 验收证据至少包含命令、计数、设备/系统版本、产物、失败与警告、人工结果和最终结论。
5. 有条件通过、未执行、阻塞或核心失败时不得提交审核，除非用户对具体风险作出明确发布决定。

## 2. 创建应用与发布资料骨架

若 AppGallery 尚无应用：

1. 先取得对“在指定账号创建应用”的明确授权。
2. 选择或创建所属项目。项目是 AppGallery Connect 中组织多个应用及共享服务配置的容器，不是应用分类；未来多个独立应用可按产品线或隔离要求分项目。
3. 创建 HarmonyOS 应用，确认应用名称、应用/游戏分类、支持设备和最终 Bundle Name。Bundle Name 一旦进入签名与平台绑定后不要随意修改。
4. 在页面要求下准备图标、手机/平板截图、应用简介、详细介绍、关键词、更新说明和分类。尺寸、格式、数量以当前上传控件为准。

## 3. 发布证书、Profile 与 DevEco 签名

1. 在 DevEco Studio 生成或选择本地密钥库和 CSR。密钥库密码与别名密码只由用户在本机输入。
2. 在 AppGallery Connect 创建 release 证书并上传 CSR；下载 release 证书。
3. 创建 release Profile，绑定目标应用/Bundle Name、release 证书和要求的设备/能力；下载 `.p7b` Profile。
4. 在 DevEco 发布签名配置中选择 `.p12`、release 证书、release Profile 和别名。确认 Profile 类型、Bundle Name、证书有效期与目标应用一致。
5. 把密钥库、证书、Profile 和含本机绝对路径/加密凭据的本地配置保存在仓库外受控目录。不要读取、复制或提交密码；不要把私钥材料放入 Git。
6. 如果仓库跟踪了无签名的 `build-profile.json5` 基线，构建时保存原始字节、临时加载本机 release 配置，并在 `finally` 中恢复；随后运行 `git diff --exit-code -- build-profile.json5`。

创建、吊销或替换平台证书/Profile 是外部账号写入，执行前确认具体目标。不要吊销仍服务于已发布版本的证书。

## 4. 构建发布包

先设置项目要求的 DevEco 环境。典型命令：

```powershell
$env:DEVECO_STUDIO_HOME = '<DevEco Studio 安装目录>'
.\hvigorw.bat --mode module -p product=default -p module=entry@default --no-daemon test
.\hvigorw.bat --mode module -p product=default -p module=entry@default --no-daemon assembleHap
.\hvigorw.bat --mode project -p product=default --no-daemon assembleApp
```

- `assembleHap` 是模块级 HAP 构建，可用于安装/设备验证。
- `assembleApp` 是工程级 APP 构建；AppGallery 正式上传选择签名 `.app`。
- 若项目的 product/module 名称不同，先运行 Hvigor 任务列表并读取项目配置，不照抄示例参数。
- 记录构建开始前的 Git commit、版本、签名配置身份和构建结束时间。

## 5. 独立验包

运行 Skill 自带脚本：

```powershell
pwsh -NoProfile -File '<skill-dir>\scripts\verify-release-package.ps1' `
  -PackagePath '<signed.app>' `
  -DevEcoStudioHome '<DevEco Studio 安装目录>'
```

脚本必须同时得到：

- `verify-app success`
- `Digest verify result: true`
- `verify-profile success`
- `.app` 内 `pack.info` 的 Bundle Name、版本、构建版本、API 和设备类型
- 文件字节数与 SHA-256

把脚本输出与 `AppScope/app.json5`、模块配置、Git commit 和发布计划交叉核对。复制到交付目录后重新计算哈希，确认副本与构建产物相同。工具生成的临时证书链/Profile/结果文件应删除；不得删除原始签名材料。

## 6. AppGallery 内容、合规与联系人

先进入 `应用信息`，禁止直接从 `准备提交` 页开始并假定基础资料已经完成。逐项填写并保存：

- 名称、简介、详情、分类、图标、截图、更新说明；
- 目标国家/地区、免费/付费、发布时间、设备类型；
- 内容分级问卷；
- 隐私政策 URL、数据处理说明、权限、SDK、广告、账号、支付、AI 或其他服务声明；
- 审核联系人、可联系邮箱和电话。

### 6.1 应用信息强制防漏检查

在离开 `应用信息` 前必须逐项取得页面证据：

1. 支持设备：记录所有已勾选设备类型。逐个打开对应素材标签页；每个标签页都必须显示已上传图标预览，不能只上传当前可见标签页。
2. 应用分类：选择且仅选择一个当前平台提供的子分类，读取输入框实际值并记录。
3. 应用标签：至少选择一个标签；选择多个标签时，必须设置一个与应用分类相关的主标签。
4. 保存：点击 `保存`，等待明确的“保存成功”反馈；仅出现上传预览不算保存成功。
5. 持久化复核：刷新或重新进入 `应用信息`，再次逐个打开支持设备标签页，确认图标、分类、全部标签和主标签仍存在。

任一项为空、只有临时预览、未设置主标签或未经过重载复核时，`Store basics` 门禁失败，不得进入最终提交摘要。

### 6.2 提交前双页预检

最终摘要前必须分别审计两页，不能用其中一页代替另一页：

| 页面 | 必须确认 |
| --- | --- |
| `应用信息` | 应用名称；每个支持设备标签页的图标；分类；标签；主标签；保存与重载结果 |
| `准备提交` | 精确软件包；加密；地区；发布时间；应用介绍/一句话简介；各设备截图；更新说明；分级；隐私与数据声明；AI 等服务声明；版权/备案；审核联系人 |

声明必须与代码和权限清单一致。可以使用华为隐私托管，但用户需亲自确认政策内容与法律声明。OTP、CAPTCHA、法定声明和协议勾选由用户完成；代理不得代替作事实保证。

## 7. 上传软件包并启动自检

上传是外部写入。先总结目标应用、版本、Bundle Name、文件名、SHA-256、地区和用途，取得针对该上传的明确授权。

1. 打开 `软件包管理`，选择上传，使用场景选语义等同于 `测试和正式上架`。
2. 上传已验证的签名 `.app`；不要上传或改名 `.hap`。
3. 等待解析完成，核对文件名、Bundle Name、版本、构建版本、设备类型、使用场景、上传时间和合法性。合法性必须达到平台允许提交的状态，例如 `已达标`。
4. 自检会消耗平台任务配额；执行前核对当前配额/并发限制并取得授权。启动后记录软件包行和任务时间。
5. 读取报告时核对报告 ID、测试时间晚于本次上传、应用版本、Bundle Name 和软件包身份。旧包仍在列表时，绝不能仅凭“最新一条”判断。
6. 自检失败就记录规则、设备、截图/日志、发生次数与报告 ID，回到本地复现、修复、重新构建和验包。新报告通过前不要关闭问题。

浏览器文件选择器不可控时，不要宣称上传成功。让用户手动选取文件后重新读取平台软件包表确认结果。

## 8. 版本选取与保存草稿

1. 进入待提交版本的 `准备提交`/版本配置页。
2. 在 `版本选取` 中选择刚核对过的 `.app`，检查版本、设备和软件包行后 `确认选取`。
3. 按当前页面和产品要求设置软件包加密；无相反要求时保留平台推荐选项，并在提交摘要中记录。
4. 完成地区、发布时间、更新说明和其他必填项，点击 `保存`。
5. 刷新或重新进入页面，确认所选软件包和字段仍然存在。保存成功不等于提交审核。

## 9. 最终提交门禁

点击 `提交审核` 前向用户展示：

- 账号/主体、应用名称、Bundle Name；
- versionName/versionCode/buildVersion；
- Git commit、软件包名、路径、字节数、SHA-256；
- `verify-app`、摘要、Profile、元数据结果；
- 平台合法性、自检报告 ID 与结论；
- 地区、价格、发布时间、隐私政策、分级、联系人；
- 已知警告、剩余风险、回退方式。

只有用户在此时明确说出等同于“将上述版本提交审核”的授权，才能点击。之前的“继续”“发布应用”“上传完成”或保存草稿都不自动覆盖该门禁。

提交后记录平台状态、提交时间、版本和可见流水信息。若页面另有“立即发布/上线”动作，需要新的动作时确认。

## 10. 状态语义与发布后检查

| 状态 | 可以声称 | 不可以声称 |
| --- | --- | --- |
| 草稿/准备提交 | 资料和包已保存 | 已提交、审核通过、已上架 |
| 已提交审核/审核中 | 平台已接收审核请求 | 审核通过、已上架 |
| 审核通过 | 审核结论通过 | 目标地区一定已可下载 |
| 已上架 | 目标地区商店页可见且版本可安装 | 所有地区都已同步 |

审核通过后，在目标地区的真实商店端核对详情页、版本号、设备兼容和下载安装。发布失败或驳回时，记录原因并把修复、重新上传、再次提交作为新的发布循环。

## 11. 最终交付记录

记录本地 commit、包哈希、验包输出摘要、平台软件包行、自检报告、提交/审核/上架时间和遗留风险。文档中可记录受控发布目录，但不得写密码、密钥、Cookie、OTP 或签名配置中的敏感字段。
