# HarmonyOS AppGallery 完整发布流程

本流程以当前源代码、产物和 AppGallery Connect 页面为准。字段、配额、设备映射和按钮名称会变化；执行时读取当前语义，并用 `appgallery-form-checklist.md` 对照当前华为官方文档。旧截图、旧报告和记忆只能用于提出检查项，不能覆盖当前证据。

## 0. 建立发布身份表和授权表

开始前记录并交叉核对：

| 字段 | 本地来源 | 平台来源 |
| --- | --- | --- |
| 开发者账号/主体 | 用户确认 | 当前登录账号 |
| 应用名称、应用 ID | 产品与发布记录 | AppGallery 应用页 |
| 安装后名称、图标 | `AppScope`、Ability 与本地化资源；实际安装 | 应用信息名称、图标与审核报告 |
| Bundle Name | `AppScope/app.json5` | 应用与软件包详情 |
| versionName/versionCode/buildVersion | 应用配置与 `pack.info` | 软件包解析行 |
| 设备类型、compatible/target API | `build-profile.json5`、模块配置与 `pack.info` | 软件包解析行、支持设备、审核报告 |
| 发布地区、价格、发布时间 | 发布计划 | 版本字段 |
| 源码身份 | Git commit、分支、工作区 | 发布记录 |

任一关键字段冲突就停止。不要用旧对话里的值覆盖当前文件或页面。

把外部动作分别列出并标记是否获授权：创建项目/应用、创建或吊销证书/Profile、上传包、启动自检、写入/保存门户字段、接受法律声明、提交审核、撤销审核、手动发布、删除旧包。一个动作的授权不传递给下一个动作。

## 1. 发布前工程门禁

1. 读取仓库 `AGENTS.md`、README、产品边界、发布文档和验收规则。
2. 检查 Git 分支、提交、工作区、远程、版本文件和待发布差异；保留可回退检查点，不混入无关改动。
3. 运行项目规定的静态检查、本地测试、集成/设备测试和人工清单。权限、数据、部署或核心流程按项目要求完成 L3 验收。
4. 验收证据包含命令、计数、设备/系统版本、产物、失败与警告、人工结果和最终结论。
5. 有条件通过、未执行、阻塞或核心失败时不得提交审核，除非用户对精确风险作出明确发布决定。

截图不仅是营销素材，也是发布验收输入。先在真实待发布版本上生成候选帧，逐张检查适配、文字可见性、隐私和画面完整性；发现缺陷就回到修复、测试、重新签名和重发循环。

## 2. 创建应用与资料骨架

若 AppGallery 尚无应用：

1. 取得对指定账号创建项目/应用的明确授权。
2. 创建或选择项目；项目是共享服务配置的容器，不是应用分类。
3. 创建 HarmonyOS 应用，确认名称、应用/游戏类型、初始设备和 Bundle Name。
4. 先建立发布素材清单：语言、素材设备组、图标、介绍截图/视频、应用介绍、一句话简介、更新说明、分类/标签、客服渠道、隐私政策、权限/SDK/AI/支付事实、版权/备案材料、审核联系人和上架时间。

Bundle Name 一旦与签名和平台绑定，不要随意修改。

## 3. 发布证书、Profile 与本地签名

1. 在 DevEco Studio 生成或选择本地密钥库和 CSR；密码只由用户本机输入。
2. 经授权在 AppGallery Connect 创建 release 证书并上传 CSR，下载 release 证书。
3. 经授权创建 release Profile，绑定目标应用/Bundle Name、release 证书和需要的受限开放权限，下载 `.p7b`。
4. 在本机 release 签名配置中选择 `.p12`、release 证书、release Profile 和别名；核对类型、Bundle Name、权限和有效期。
5. 密钥库、证书、Profile 和含绝对路径/加密凭据的配置留在仓库外受控目录，不进入 Git、聊天、截图和文档。
6. 如构建要临时改跟踪的 `build-profile.json5`，先保存原始字节，在 `finally` 恢复，随后运行 `git diff --exit-code -- build-profile.json5`。

创建、吊销或替换证书/Profile 是平台账号写入；不要吊销仍服务于已发布版本的证书。

## 4. 构建与独立验包

典型命令：

```powershell
$env:DEVECO_STUDIO_HOME = '<DevEco Studio 安装目录>'
.\hvigorw.bat --mode module -p product=default -p module=entry@default --no-daemon test
.\hvigorw.bat --mode module -p product=default -p module=entry@default --no-daemon assembleHap
.\hvigorw.bat --mode project -p product=default --no-daemon assembleApp
pwsh -NoProfile -File '<skill-dir>\scripts\verify-release-package.ps1' `
  -PackagePath '<signed.app>' `
  -DevEcoStudioHome '<DevEco Studio 安装目录>'
```

- `assembleHap` 是模块级安装/设备验证产物。
- `assembleApp` 是工程级商店容器；AppGallery 正式上传选择 release 签名 `.app`。
- product/module 名称不同时先读取工程配置和任务列表，不照抄示例。
- 独立验包必须同时得到 `verify-app success`、`Digest verify result: true`、`verify-profile success`，并解析 `pack.info`。
- 分别记录 compatible API（最低兼容）和 target API（目标能力）；不得把 target 值当成最低适配值。
- 记录路径、字节数、SHA-256、Bundle Name、版本、构建版本、API 和设备类型。复制到交付目录后重算哈希。
- 在每个发布设备组实际安装候选 HAP，核对桌面/启动器名称和图标与应用信息完全一致；只读资源引用不能替代终端证据。
- 删除验包生成的临时导出文件，不删除原始签名材料。

`BUILD SUCCESSFUL`、已签名 HAP、文件扩展名和门户旧记录均不能替代上述证据。

## 5. 先完成 `应用信息`

进入 `应用上架 > 应用信息`，按 `appgallery-form-checklist.md` 完成：

1. 读取支持设备，并与包内设备范围、兼容分发和 PC/2in1 提示对齐。
2. 循环每种语言，配置应用名称；记录默认语言回退是否有意。
3. 循环每个素材设备组上传图标。当前手机和平板共用 `手机/平板`，智能手表和运动手表共用 `手表`；不要按原始设备枚举发明重复页签。
4. 选择一个分类；最多 5 个标签，并设置一个与二级分类关联的主标签。
5. 填写适用的开发者服务信息；官网/客服渠道/应用内反馈路径必须真实可用。
6. 点击保存，读取明确反馈；刷新或离开后重进，重新循环每种语言和素材设备组，核对图标、名称、设备、分类、标签、主标签和服务信息仍存在。
7. 将每种语言的门户名称/图标与该设备组安装后的终端名称/图标并排核对；任何一个 AppScope、Ability、本地化回退或图标槽位不一致都标记 `BLOCKED`。

只有上传预览没有保存/重载证据时，本阶段失败。

## 6. 上传软件包、合法性与上架自检

上传是外部写入。先展示应用、版本、Bundle Name、文件名、路径、字节数、SHA-256、地区和用途，取得针对精确文件的授权。

1. 打开 `应用上架 > 软件包管理 > 上传`。
2. 先选择 `测试和正式上架`，再选择已验证的 `.app`。文件选择器不可控时由用户手动选择；之后必须回读软件包表。
3. 等待解析，逐列匹配文件名、包名、版本、构建版本、设备、使用场景、上传时间和合法性。
4. `不通过` 阻止发布。官方上传页称 `待优化` 允许提交但有风险，版本选取页又把 `已达标` 列为选择前提；默认只放行 `已达标`。只有当前选取窗口明确允许该精确 `待优化` 包、报告已读取且用户针对该报告明确接受风险时才可继续，否则保持 `BLOCKED`。
5. 上架自检是官方推荐项。启动前说明当前精确包、任务并发/配额影响，取得授权；没有运行时在最终摘要明确写出。
6. 自检报告按报告 ID、起止时间、包/版本、设备任务和软件包记录绑定；超时或页面没有新报告时保持等待，不重复启动。
7. `待优化` 不等于 `通过`。官方允许合法性通过的包继续提交，但先展示报告和驳回风险，由用户决定修复或接受风险。

自检发现真实问题时保存报告证据，回到本地复现、测试、生成新的签名 APP、验包、重新上传和新报告；旧报告不能关闭新包的问题。

## 7. 选择版本并完成 `版本信息/准备提交`

1. 在 `软件版本 > 版本选取` 默认选择刚核对的 `测试和正式上架`、合法性 `已达标` 包；若按第 6 节的严格例外选择 `待优化` 包，把报告和用户风险决定带入最终摘要。
2. 回读文件名、版本、构建版本、上传时间和设备后确认选取；保存并重进版本，再次读取“已选软件包”。上传行存在但版本仍显示旧文件时不得继续。
3. API Level ≥ 11 时记录加密/不加密选择及理由；只有运动手表不支持加密。
4. 按 `appgallery-form-checklist.md` 逐行完成：
   - 发布地区与适用的数据出境声明；
   - 每种语言的介绍、一句话简介、新版本特性；
   - 每个素材设备组的截图、视频和适用推荐图；
   - 应用内资费与商品；
   - 内容分级问卷的保存、验证、提交和回写；
   - 权限隐私说明、隐私政策/权利、隐私标签；
   - AI 功能声明；版权证明/授权材料；APP 备案或单机/境外类型；
   - 审核测试账号、备注/自测文件、负责人姓名/手机/邮箱/验证码；
   - 审核通过立即上架或指定时间。
5. 法律条款、隐私托管协议、数据出境声明、权利/版权事实和短信验证码由用户本人处理。
6. 保存，刷新或重进版本，重新读取精确软件包和全部字段。

三个隐私区域不可合并：

- `应用隐私说明` 对应包内敏感/受限权限及使用理由/视频；
- `隐私声明` 对应自定义隐私政策入口与隐私权利入口，或已生成并关联的托管政策；两个字段即使允许使用同一 URL，也要分别验证相应内容；
- `隐私标签` 对应个人信息收集、业务场景和数据项。

公开隐私 URL 在填写前必须实际访问。404、占位页、登录墙或与应用行为不符时停止。托管政策生成后仍要回版本页选中并保存。

## 8. 双页持久化预检

创建字段状态表，每行只允许 `PASS`、有证据的 `N/A`、`UNKNOWN` 或 `BLOCKED`。

| 页面 | 必须审计 |
| --- | --- |
| `应用信息` | 支持设备；语言；每种语言名称；每个素材设备组图标；分类；标签；主标签；开发者服务信息；保存/重载 |
| `版本信息/准备提交` | 精确包与加密；地区；每种语言介绍/一句话/特性；每个素材设备组截图/视频；资费；分级；三组隐私；AI；版权；备案；审核信息/联系人；上架时间；保存/重载 |
| `软件包管理` | 精确上传行；合法性；自检状态/报告或明确的未运行风险 |

任一必填/适用行是 `UNKNOWN`、`BLOCKED`、空值、过期或未保存时，不得呈现“已准备完成”的最终提交摘要。

## 9. 最终提交门禁

点击 `提交审核` 前向用户展示：

- 账号/主体、应用名称、Bundle Name；
- versionName/versionCode/buildVersion；
- Git commit、软件包名、路径、字节数、SHA-256；
- `verify-app`、摘要、Profile 和元数据结论；
- 软件包上传时间、合法性、自检报告 ID/结论或明确的跳过风险；
- 当前版本保存并重载后的已选软件包行；
- 应用信息和版本信息字段状态表；
- 地区、资费/价格、上架时间、隐私方式、分级、版权/备案和联系人验证；
- 已知警告、风险、`N/A` 理由和回退点。

只有用户在此时明确授权“将上述精确版本提交审核”，才能点击。之前的“继续”“发布应用”“上传完成”“准备好”或保存草稿都不覆盖该门禁。

提交确认窗再次核对版本号和支持设备提示。提交后记录平台回执、时间、版本和按钮变化。

## 10. 状态语义与发布后验收

| 状态 | 可以声称 | 不可以声称 |
| --- | --- | --- |
| 草稿/准备提交 | 资料和包已保存 | 已提交、审核通过、已上架 |
| 预审中/已提交/审核中 | 平台已接收审核请求 | 审核通过、已上架 |
| 审核通过/待上架 | 审核结论通过 | 目标地区一定已可下载 |
| 已上架 | 已在核对的目标地区商店页可见且版本可安装 | 所有地区都已同步 |

审核通过后：

1. 若配置立即上架，等待商店传播并在目标地区真实商店端核对详情页、名称、图标、截图、隐私入口、版本号、设备兼容和下载安装。
2. 若配置指定时间，保持 `待上架`；提前 `手动发布` 是新的外部动作，需要新授权。
3. 驳回时进入第 11 节；旧报告只说明被审核软件包，不代表本地候选包或后续上传包的状态。
4. 维护版本仍需重新审查受变化影响的分级、隐私、权限、SDK、AI、商品、备案、素材和更新说明。

## 11. 审核驳回后的修复与重提闭环

### 11.1 冻结审核报告身份

先只读保存审核原文并建立“审核报告身份”：

| 字段 | 必须读取的当前证据 |
| --- | --- |
| 报告 | 报告 ID/URL、提交审核时间、报告生成时间、测试环境、应用名称、Bundle Name、版本 |
| 被审核软件包 | 失败版本页当前已选文件名、versionName/versionCode/buildVersion、上传时间、设备 |
| 本地候选 | commit、文件名、字节数、SHA-256、签名/Profile、compatible/target API、设备 |

优先用报告自身、提交时保存的版本快照或平台不可变历史记录证明被审核软件包。失败版本页的“当前已选软件包”只代表读取时状态：只有能证明提交后未改选时，才可用它补全报告缺少的文件名。

若页面可能已在驳回后改选，且无法用报告、提交快照或不可变记录唯一证明原包，被审核软件包保持 `UNKNOWN/BLOCKED`；不得把当前已选包倒推为审核包，也不得生成重提摘要。若本地候选与已证明的被审核软件包不同，只能结论为“本地另有候选”；不得宣称审核已覆盖本地修复。

### 11.2 建立驳回问题矩阵

每个问题占一行，只允许 `OPEN`、`VERIFIED_LOCAL`、`VERIFIED_PACKAGE`、`VERIFIED_PORTAL` 或 `BLOCKED`：

| 原始审核问题 | 被审核软件包证据 | 根因类别 | 修改面 | 验证命令/人工步骤 | 是否需新 APP | 当前状态 |
| --- | --- | --- | --- | --- | --- | --- |
| 原文，不改写为更轻的表述 | 文件/版本/上传时间 | 应用信息、文案、包配置、兼容、功能价值/可达性、运行缺陷或旧包误选 | 源码、产品、素材、门户或组合 | 可复现证据 | 是/否及理由 | 状态 |

根因未证实时保持 `OPEN`；仅改门户文字不能关闭包配置、兼容或功能问题。所有受影响行到 `VERIFIED_PORTAL` 后才可生成重提摘要。

### 11.3 四类常见驳回门禁

1. **名称/图标不一致**：对比每种语言的 AppGallery 名称/图标、AppScope 资源、EntryAbility 资源、默认语言回退和各发布设备组安装后的终端名称/图标。只改一处资源或只看门户预览不通过。
2. **一句话简介不完善**：使用符合当前字符限制的完整功能句，明确真实的用户动作或结果；营销口号、关键词堆砌、句子残缺或无法证实的收益均为 `BLOCKED`。同时核对介绍、截图和实际功能一致。
3. **最低适配版本过高**：分别读取源码 `compatibleSdkVersion`/`targetSdkVersion`、新 APP 的 `pack.info`、门户解析行和被审核软件包。降低 compatible API 前检查全部 API 调用和依赖并补兼容测试；不能只改配置数字。
4. **功能或场景有限**：列出从干净安装开始可完成的核心用户闭环、入口和前置条件。若真实产品价值不足，回到产品与源码扩充并重新验收；若功能被时间、账号、外设或数据条件阻塞，提供正常用户可用的到达路径或受支持的审核环境/测试账号。审核备注和自测视频只能补充说明，不能替代实际可用功能。

不得为了审核植入仅审核员可见的调试开关、伪造统计或正式包测试数据。

### 11.4 生成替换包并关闭门户证据

只改持久化的应用信息且不影响包时可复用已验证 APP；任何源码、资源、SDK、权限、依赖或功能变化都必须重新测试、签名、验包和上传。

1. 完成项目规定的测试和独立验收；生成新 APP 并记录新的唯一身份。
2. 经授权上传，读取新软件包行；不得凭相似版本名猜测。
3. 在失败版本中选中新包，保存、离开并重进，回读已选文件名/版本/构建版本/上传时间。
4. 更新受影响的名称、介绍、一句话简介、截图、视频、审核备注和自测文件；保存并重载。
5. 将驳回问题矩阵逐行更新到 `VERIFIED_PORTAL`，同时保留旧报告与被审核软件包身份，形成前后差异。

### 11.5 重新提交授权与新报告

重提摘要必须同时展示旧报告/被审核软件包、新 commit/新 APP、新已选软件包、每个问题的关闭证据、未消除风险和回退点。只有用户针对该摘要明确授权“重新提交此精确版本审核”时才能点击；旧的提交授权不延续。

重新提交后记录新提交时间和状态。若再次驳回，新报告必须重新绑定当次已选软件包，不能沿用旧矩阵的 `VERIFIED_PORTAL` 结论。

## 12. 最终交付记录

记录本地 commit、包哈希、验包输出摘要、平台软件包行、当前已选软件包、自检报告、字段状态表、提交/审核/上架时间和遗留风险。发生驳回时再记录审核报告身份、被审核软件包、驳回问题矩阵、替换包和重提授权。不得记录密码、测试账号秘密、私钥、Cookie、OTP、短信验证码或签名配置中的敏感字段。
